# v548 수업일지 전송 복구 · 미전송 관리

## 확인된 원인 (2026-09-30 KST)

운영 Firestore의 미전송 10건 모두 `NOTION_SCHEMA_SETUP_REQUIRED`, 생성 전 `phase: new` 상태였다. Notion 데이터 소스의 다른 필수 항목은 존재했지만 `Portal draft ID` rich_text 속성이 없었다. 누가 언제 제거했는지는 확인하지 않았다. 제출 원본은 Firestore에 남아 있었다.

누락 속성을 복구하고 기존 활성 페이지 2개의 원래 식별자를 복원했다. 휴지통에 있던 1개 페이지는 건드리지 않았다. `Portal draft ID`는 중복 전송 확인용이므로 삭제하거나 타입을 바꾸지 않아야 한다. 새로운 속성을 무조건 자동 생성하는 코드는 넣지 않았다.

## 동작

- 관리자만 수업일지의 다섯 번째 탭 **미전송 관리**를 이용한다. Firestore 원본 컬렉션을 직접 조회하며 별도 복사 DB의 불일치를 만들지 않는다.
- 전송 중·재시도 대기와 확인 필요 기록을 강사/상태별로 필터링한다. 페이지당 40건이며 각 페이지의 확인 필요 항목을 선택해 일괄 재처리한다.
- 강사·학생·수업일·제목·제출/최근 갱신 시각·시도 횟수·실패 사유·원본 보기를 제공한다. 모바일 표는 가로 스크롤한다.
- 접수/이미 처리 중 또는 완료/접수 실패 건수를 구분한다. 접수는 Notion 전송 성공이 아니다. 새로고침으로 실제 결과를 확인한다.
- 재처리는 제출된 snapshot, 작성자, 전송 목적지를 유지한다. `retryHistory`에 요청자·시각·이전 오류를 저장한다. 관리자 대리 작성/수정 권한은 부여하지 않는다.
- 네트워크, 429, 5xx, 첨부 처리 대기는 30초부터 지수적으로 간격을 늘리며 최대 5회 실패 후 수동 확인 대상으로 둔다. Retry-After는 최대 1시간 범위에서 반영한다. 분 단위 스케줄러 때문에 실제 시각은 더 늦을 수 있다.
- POST 결과가 불확실하면 기존 페이지를 먼저 조회한다. 명시적으로 거절된 해당 생성 요청만 새 생성 시도를 허용한다. 이전 불확실한 생성 상태를 후속 사전 점검 오류로 초기화하지 않는다.
- 스케줄러는 처리 중/대기 중인 첫 항목들을 건너뛰고 페이지를 순회해 준비된 항목을 찾는다. 함수/문서 트랜잭션의 임대는 중복 실행을 막는다.

## 재발 시

`NOTION_ID_PROPERTY_MISSING`는 관리자 설정 확인 대상이다. 임의로 새 일지를 만들거나 실패 원본을 삭제하지 않는다. 기존 제출 페이지의 연결을 확인한 뒤 `scripts/repair-lesson-notion-schema.cjs`의 기본 읽기 전용 점검을 실행한다. `--apply`는 필요한 속성/활성 페이지 식별자만 복구한다. 인증은 승인된 운영 자격 증명을 환경 변수로 제공하고 토큰이나 자격 증명 파일 내용을 출력하지 않는다.

배포 범위는 `teacherPortalLessonLogs`, `teacherPortalLessonLogSync`, `teacherPortalLessonLogWritten` 세 함수와 정적 포털 파일이다. 의존성·보안 규칙·다른 함수는 변경하지 않았다.
